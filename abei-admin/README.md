# abei-admin

阿贝后台。维护解析规则的人用的那一面。

## 为什么和 abei-web 分开

前台（abei-web、CLI、以后的 iOS）面对的是记账的人：看账、对账、问助手。
后台面对的是维护阿贝本身的人：调解析器、配同步器、处理别人提的反馈。

这两拨人的导航、权限模型和发版节奏都不一样。塞在同一个应用里，代价是前台的一级导航
被三个普通用户永远点不开的入口占着，而后台想加个宽表格又得先照顾手机端布局。
所以是两个应用，不是一个应用的两个路由段。

共享的只有设计 token 和几个基础组件，而且是**复制**过来的，没有共享包：
后台的表格密度、动效取舍本来就该能独立演进，共享包只会让每次改动都要顾及另一边。

## 三个页面

| 路径       | 做什么                                             |
| ---------- | -------------------------------------------------- |
| `/mail`    | 邮件工作台：看原始邮件、定样本、配收件邮箱（同步器） |
| `/parser`  | 解析器工作台：编解析流程、跑样本、看解析结果         |
| `/feedback`| 反馈管理：归一、处理、向用户同步进展                 |

`/` 直接跳 `/mail`。后台不需要「概况」。

## 权限

整站被 `OwnerGate` 挡在门口——不是每个页面各写一遍检查，那样只要漏掉一个新页面就是个洞。
门口挡的好处是新页面默认受保护。

这不是安全边界：服务端 `/v1/admin/*` 自己校验 owner，`OwnerGate` 只负责别让非 owner
对着一屏 403 发呆。登录复用前台那套 Firefly 个人访问令牌，令牌只留在当前浏览器会话。

## 开发

```bash
npm install
npm run dev          # 127.0.0.1:5175，/v1 反代到本机 abei-api:18002
```

5175 是固定的：5173 归前台的 dev，5174 归前台 e2e 自起的那个，后台只能往后排。

## 验证门

四条都要绿，缺一不可：

```bash
npm run typecheck    # 不是 npx tsc --noEmit，那个是假绿灯
npm run lint
npm run test:run
npm run build
```

## 部署

`compose.yml` 里的 `abei-admin` 服务，多阶段构建后是纯 nginx，默认 `127.0.0.1:18006`
（`ABEI_ADMIN_PORT` 可改）。nginx 只反代 `/v1` 给 abei-api——后台不跑助手，
也不该成为绕过 abei-api 直连 Firefly 的口子。
